# B.M.O. Android Bridge Protocol v1

This document is the wire contract between `MCP_PC_CONTROLLER` and
`MCP_ANDROID_EXTENSIONS`.

## Topology

```text
MCP client / ChatGPT
        |
        v
MCP_PC_CONTROLLER :8765
        |
        v
AndroidGateway 127.0.0.1:8767
        ^
        | Cloudflare Named Tunnel (same public hostname, /android)
        |
        +--------- outbound WSS -------- Android
```

Android never listens on a public socket. The phone opens the WSS connection,
which means NAT, carrier-grade NAT, 4G/5G and unrelated Wi-Fi networks do not
change the control model.

## Transport

- WebSocket over TLS (`wss://`) on the public side.
- JSON UTF-8 text messages.
- Protocol version: `1`.
- Maximum gateway WebSocket message: 6 MiB.
- Camera frame: JPEG, normally <= 1280 px wide, base64 inside a bounded result.
- Audio: mono PCM signed 16-bit little-endian, 16 kHz, base64, maximum 10 s.
- RPC IDs are random UUID-derived strings generated by the MCP host.
- MCP host applies a bounded timeout and suppresses late/unknown result IDs.
- Successful MCP-side RPC results include `round_trip_ms` for end-to-end device latency.
- Camera capture rejects frames older than 2500 ms instead of presenting stale vision as live.

## Pairing

MCP creates a one-use six-digit code with `android_create_pairing`.
The code expires after a bounded TTL.

Phone -> gateway:

```json
{"type":"pair","device_id":"...","pairing_code":"123456"}
```

Gateway -> phone:

```json
{"type":"paired","device_id":"...","credential":"...","expires_at":0}
```

The phone stores the credential encrypted with Android Keystore AES-GCM.
The gateway stores only its SHA-256 digest. Invalid pairing attempts are
rate-limited. The Cloudflare credential is never present on Android.

The phone then sends:

```json
{
  "type":"hello",
  "device_id":"...",
  "credential":"...",
  "platform":"android",
  "protocol_version":1,
  "app_version":"0.1.0",
  "capabilities":{
    "camera":true,
    "microphone":true,
    "speaker":true,
    "overlay":true,
    "vibrate":true
  }
}
```

Gateway accepts only protocol v1 and returns:

```json
{"type":"ready","device_id":"...","protocol_version":1}
```

## RPC

Gateway -> Android:

```json
{"type":"command","id":"...","op":"capture_frame","args":{}}
```

Android -> gateway:

```json
{"type":"result","reply_to":"...","ok":true,"payload":{}}
```

Errors use `ok:false` and a bounded `error` string.

## Operations

| Operation | Direction | Purpose |
|---|---|---|
| `ping` | PC -> phone | End-to-end latency/readiness |
| `capture_frame` | PC -> phone | Return latest camera JPEG |
| `record_audio` | PC -> phone | Return bounded PCM16 microphone clip |
| `speak` | PC -> phone | Speak text with Android TTS |
| `draw_circle` | PC -> phone | Draw guidance over camera preview |
| `clear_overlay` | PC -> phone | Remove visual guidance |
| `vibrate` | PC -> phone | Short tactile cue |

`android_hear` is an MCP composite: it calls `record_audio` and sends the
transient WAV representation to the existing isolated faster-whisper worker on
MCP_HOST. The temporary WAV is deleted after transcription. Microphone capture
is serialized; a concurrent request fails explicitly with `MICROPHONE_BUSY`.

## Visual coordinates

`draw_circle` uses normalized coordinates relative to the JPEG returned by
`android_camera_frame`:

- `x=0` left, `x=1` right;
- `y=0` top, `y=1` bottom;
- `radius` is normalized against the shorter frame dimension.

The Android overlay reproduces CameraX `FILL_CENTER` center-crop geometry, so
a point identified in the returned frame maps to the same visible point in the
phone preview.

## Cloudflare routing

The existing B.M.O. Named Tunnel can carry both MCP and Android:

```yaml
ingress:
  - hostname: mcp.example.com
    path: /android.*
    service: http://127.0.0.1:8767
  - hostname: mcp.example.com
    service: http://127.0.0.1:8765
  - service: http_status:404
```

With `cloudflare_hostname=mcp.example.com`, the MCP derives
`wss://mcp.example.com/android` unless `android_public_ws_url` explicitly
overrides it.

## Privacy and lifecycle

Camera frames and microphone bytes are transient and are not stored by the
Android app. The camera analyzer runs while the app Activity is visible.
The tunnel is maintained by a foreground service and reconnects with bounded
exponential backoff. Microphone capture uses the foreground service and the
normal Android runtime permission.

A transport ACK/result only proves that the device operation completed. Visual
guidance should use a fresh `android_camera_frame` when confirmation matters.
